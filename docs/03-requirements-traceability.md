# 03. 요구사항 상세와 추적표

작성일: 2026-09-23  
기준: [제품 명세 v0.1](../agent_workspace_spec_v0.1.md), 커밋 6f719123c2e812362697e9ebe0deb8b31557b09b  
연결: [기술 검증](01-technical-validation.md), [아키텍처 결정](02-architecture-decisions.md)

## 1. 관리 규칙

REQ는 제품이 해야 할 일, ADR은 구현 방향, TV는 기술 검증을 뜻한다. 아래 48개 요구사항은 모두 첫 버전 범위이며 우선순위 P0(출시 필수)다. P0가 한 번에 모두 구현한다는 뜻은 아니다. 기반 검증 → 핵심 흐름 → 동시 작업 → 통합·복구 → 성능 순으로 구현한다.

현재 모든 항목은 **미구현·미검증**이다. 문서 작성으로 완료 처리하지 않는다. 행의 입력·출력, 수용 기준, 예외 처리가 검증의 기준이다. '설계'라고 표시한 세부는 사용자 요구를 충족하기 위한 내부 선택으로, 제품 요구를 변경하지 않는 범위에서 ADR로 바꿀 수 있다.

원문에 없는 구체적인 시간·메모리 수치를 임의로 사용자 확정 사항으로 추가하지 않는다. 요구사항 ID는 유지하며 삭제된 ID를 다른 기능에 재사용하지 않는다.

## 3. 핵심 경계 시나리오

### AC-001 — 두 작업의 동시 실행과 전환

사전 조건: 서로 다른 워크트리 A/B, 두 엔진 실행 중, A 서버 실행·디버깅 연결.

조작: A 코드를 열고 미저장 편집 → B 선택 → B 코드·터미널 확인 → A 복귀.

기대: 각 화면이 해당 워크트리를 가리킨다. 두 에이전트와 A 서버·디버거는 유지된다. A 편집 버퍼와 커서가 보존된다. 분석 서비스를 전환 때문에 재시작하지 않는다. 연결: REQ-007, REQ-018, REQ-024~027.

### AC-002 — 대기열 경계와 중단

사전 조건: A 실행 중, 대기 지시 M1/M2/M3.

조작: M2 수정, M3 삭제, M1 전달 전후에 Esc, 이후 새 지시로 재개.

기대: 삭제된 M3는 실행하지 않는다. M1 상태는 대기/전달 중/수락 중 하나로 정확히 구별된다. 중단은 자동 소비를 멈춘다. 재개 후 같은 항목을 두 번 보내지 않는다. 연결: REQ-012, REQ-013, REQ-016, REQ-017.

### AC-003 — 연결 단절 시 중복 방지

사전 조건: 에이전트가 커밋 등 부작용 있는 동작을 실행 중.

조작: 응답 수신 전 연결 단절 → 자동 복구.

기대: 로컬 저널·엔진·Git 상태를 확인한다. 결과를 확인할 수 없으면 불명 상태로 대기하고 같은 동작을 자동 재실행하지 않는다. 다른 작업은 계속한다. 연결: REQ-019, REQ-033.

### AC-004 — 충돌을 가진 반영 순서

사전 조건: 동일 저장소에서 A/B/C 완료. A 반영 후 B는 충돌하며 C는 독립 변경.

조작: 순차 반영, B 충돌 상태에서 C 평가.

기대: B 상태를 보존하고 C는 최신 대상 기준으로 처리한다. B의 해결 파일·다른 작업의 코드를 덮지 않는다. 작업 간 의존 실행을 자동 추가하지 않는다. 연결: REQ-033, REQ-034.

### AC-005 — 기존 세션 가져오기

사전 조건: 원본 폴더에 추적 수정·삭제·미추적 파일과 기존 OMP 대화.

조작: 일부 파일만 선택해 새 워크트리로 가져오고 추가 지시.

기대: 선택 변경만 대상에 반영, 원본 불변, 대화 문맥 유지, 새 수정은 새 경로에서 발생한다. 복사 도중 원본 변경 시 성공으로 위장하지 않는다. 연결: REQ-029, REQ-030.

### AC-006 — diff의 실제 줄 보존

사전 조건: 한쪽에만 10줄 삽입, 원래 빈 줄, 파일 전체 삭제, 긴 줄 사례.

조작: 좌우 비교, 독립 스크롤, 변경 블록 탐색.

기대: 각 뷰에 실제 파일의 줄만 존재하고 정렬용 빈 행은 없다. 블록 탐색은 대응 경계를 가리킨다. 실제 빈 줄을 삭제하지 않는다. 연결: REQ-039, REQ-040.

## 6. 구현 상태 업데이트 양식

각 기능 구현 PR 또는 작업 기록에 다음을 작성한다. 실제 코딩이 시작되면 별도 상태표를 추가하되 이 요구사항의 정의를 복제하지 않는다.

```text
REQ ID:
구현 상태: 미착수 | 진행 중 | 차단 | 검토 대기 | 완료
관련 ADR / TV / AC:
수정 모듈·파일:
수용 기준별 실행 결과:
예외·경계 확인 결과:
증거·커밋:
남은 제한 또는 차단 사유:
```

완료 조건은 코드 존재, 수용 기준 충족, 필요한 증거 확보다. Windows 기능을 Linux 모의 시험만으로 완료 처리하거나, API 수락을 실제 실행 완료로 간주하지 않는다.

## 7. 문서 간 우선순위

확정 제품 요구사항의 출처는 제품 명세와 사용자 결정이다. 본 추적표는 구현 가능한 단위로 분해한 기준이다. 충돌을 발견하면 해당 원문·REQ·ADR을 함께 수정하고 변경 이유를 기록한다. 기술 한계로 제품 범위를 줄여야 한다면 별도 변경 제안으로 다루며 코딩 에이전트가 조용히 축소하지 않는다.

검증 수치와 절차의 권위 문서는 01, 구현 방식의 권위 문서는 02다. API 필드·DB 스키마·화면 상세는 후속 문서에 정의한다. 이 세 문서만으로 모든 기술 불확실성이 해소되었다고 주장하지 않는다.
